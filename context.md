## 1. What this is

An online examination system used to assess fresher candidates during hiring at Cloudus Infotech. Candidates sit the exam on supervised office PCs; the app draws a different randomized paper per candidate, auto-saves answers, scores automatically, and produces results for the hiring team.

**Explicitly not built:** candidate accounts, webcam/screen proctoring, email sending, candidate-facing results, question analytics, mobile-first design.

## 3. The exam

### 3.1 The blueprint — `lib/exam-settings/exam-blueprint.ts`

Section shapes are **domain rules in code**, not admin settings. One source array drives every other export:

| code | ordinal | name | questions | marks each | total |
|---|---|---|---|---|---|
| `JS` | 3 | Programming Fundamentals | 10 | 1 | 10 |
| `BUG` | 5 | Debugging | 6 | 1.5 | 9 |
| `LRN` | 7 | Learn-and-Apply | 6 | 2.5 | 15 |
| `LOG` | 1 | Logic & Patterns | 10 | 1 | 10 |
| `NUM` | 2 | Number Reasoning | 6 | 1 | 6 |
| `OUT` | 4 | Output Prediction | 8 | 1.5 | 12 |
| `STP` | 6 | Steps Problem Solving | 4 | 2 | 8 |

`TOTAL_QUESTIONS = 50`, `TOTAL_MARKS = 70` across all seven.

**`code` is canonical** — it is what `Question.section` stores and what all live logic compares against.

**`ordinal` is historical only** — it exists solely for two legacy structures: the `AttemptQuestion.section` snapshot and the `section_1_score`…`section_8_score` columns. The non-sequential ordinals (3, 5, 7, 1, 2, 4, 6) are deliberate and **must not be renumbered**: doing so would change the meaning of `AttemptQuestion.section` on every paper already sat and point the score columns at the wrong sections.

Learn-and-Apply constants: `LESSON_SECTION = "LRN"`, `LESSON_GROUPS_PER_PAPER = 2`, `QUESTIONS_PER_LESSON_GROUP = 3`.

Other exports: `SECTION_CODES`, `SECTION_BLUEPRINT`, `VALID_SECTIONS`, `sectionBlueprint(code)`, `sectionBlueprintByOrdinal(ordinal)`, `isSectionCode`, `resolveSectionCode(raw)` (trim + uppercase; unknown → `null`, never defaulted), `sectionName`, `sectionNameByOrdinal`, `starvedSections(sections)`.

### 3.2 ⚠️ What a candidate actually sits today

The `exam_section_settings` migration seeds **only JS, BUG and LRN enabled**; LOG, NUM, OUT and STP ship disabled. So the live paper is:

**22 questions, 34 marks** — not the 50/70 blueprint total, and not the 55/70 the README and requirements document describe.

The 55/70 figure comes from the original spec, which included a Section 8 "Attitude" (5 unscored free-text questions) that has since been removed from the schema and the active blueprint. Treat every "55 questions / 70 marks" in `README.md` and `docs/exam-app-requirements.md` as historical.

### 3.3 Admin-editable settings — `lib/exam-settings/index.ts`

Singleton row, `id = "singleton"` (`SETTINGS_ID`).

| Setting | Default | Rules |
|---|---|---|
| `examName` | `CloudUS Online Exam` | required, trimmed, ≤ 120 (`EXAM_NAME_MAX`) |
| `durationMinutes` | 75 | whole number, 1–1440 |
| `isOpen` | **false** | `open` / `closed` only — ships closed so a fresh deploy cannot admit candidates |
| `easyPercent` / `mediumPercent` / `hardPercent` | 40 / 40 / 20 | whole percentages, must total exactly 100 |
| `unauthorizedActivityLimit` | 3 | whole number, 1–20 |

Reads are **deliberately uncached** — a stale `isOpen: true` after an admin closes the exam would let candidates in. It is a single primary-key lookup.

`getActiveSectionCodes()` reads `exam_section_settings`; **a missing row reads as enabled**, so a blueprint section added in code before its settings row is seeded behaves as it always has.

`setSectionEnabled(code, enabled)` refuses to leave zero sections enabled (`LAST_SECTION` error). The disable path runs its guard and its write inside one **`Serializable`** transaction, because a read-then-write outside one lets two concurrent disables both see two active sections, both pass, and between them leave zero — a bricked state recoverable only by a direct database edit.

`examBlueprintSummary()` returns per-section `enabled` + `available` (active questions in the bank) and totals **only the active sections**.

### Database-enforced constraints (hand-written in migration SQL, not expressible in Prisma schema)

```sql
-- One active attempt per candidate. Partial unique index.
CREATE UNIQUE INDEX "attempts_one_in_progress_per_candidate"
    ON "attempts" ("candidate_id") WHERE "status" = 'in_progress';

-- A drawn paper always records all four options.
attempt_questions_shuffled_option_order_check
    CHECK (array_length("shuffled_option_order", 1) = 4)

-- Settings really is a singleton, and its duration is sane.
exam_settings_singleton_check          -- id must be 'singleton'
exam_settings_duration_check           -- 1..1440
exam_settings_difficulty_mix_check     -- the three percentages total 100

-- A stored total can never fall outside what a valid paper can produce.
attempts_total_score_range_check
    CHECK ("total_score" IS NULL OR ("total_score" >= 0 AND "total_score" <= 70))
```

Because the partial index is absent from `schema.prisma`, **`prisma migrate diff` always reports it as drift** — this is expected and documented in the migration.

## 5. Database client — `lib/db/index.ts`

```ts
export const TRANSACTION_OPTIONS = { maxWait: 10_000, timeout: 15_000 } as const;
export const prisma: PrismaClient;
```

**Connection budget.** Postgres `max_connections = 60`, less 3 superuser and ~13 held by Supabase's own services, leaves ~40 for the application **across every instance**:

```
instances × POOL_SIZE <= 40
```

`DATABASE_POOL_SIZE` defaults to 8 and is **clamped at 20** — a single instance must not be able to claim the whole cluster budget and starve its siblings. Scale by adding instances, not by raising the pool.

**Transaction timeouts, measured not guessed.** Prisma's 2s `maxWait` default is what actually broke under load: at ~110 ms RTT an interactive transaction costs several round trips, requests queue, and once the queue is deeper than 2s Prisma aborts with **P2028** before Postgres does any work.

```
N=200, pool=50, maxWait=2000ms   -> 96 of 200 failed (P2028)
N=200, pool=50, maxWait=10000ms  ->  0 of 200 failed
N=500, pool=25, maxWait=10000ms  ->  0 of 500 failed
```

10s is long enough to absorb a start/submission spike and well under the exam client's 30s flush timeout, so a save that cannot get a connection fails and is retried rather than silently dropped. The client is cached on `globalThis` so dev hot-reload does not open a new pool per reload.

## 6. Authentication & sessions

Two completely separate session systems. Both store a random 256-bit token in an httpOnly cookie and keep **only its SHA-256 hash** in the database, so a leaked dump cannot be replayed. SHA-256 rather than bcrypt is correct here: the token is CSPRNG output, so it is unguessable and needs no key stretching.

| | Admin | Candidate |
|---|---|---|
| Cookie | `cloudus_admin_session` | `cloudus_exam_session` |
| Table | `admin_sessions` | `exam_sessions` |
| TTL | 8 hours | 12 hours (comfortably longer than any exam) |
| Flags | `httpOnly`, `sameSite=lax`, `secure` in production, `path=/` | same |
| Meaning | authentication | a **capability scoped to one attempt**, issued after eligibility is already proven |

Expired rows are deleted as they are encountered, which keeps both tables tidy without a scheduler.

- `lib/auth/password.ts` — bcryptjs, `BCRYPT_COST = 12`. bcryptjs (pure JS) rather than argon2 because the latter needs node-gyp in the Amplify Lambda bundle.
- `lib/auth/require-admin.ts` — `requireAdmin()` redirects to `/admin/login` when there is no session.

**Guard placement rule.** `app/admin/layout.tsx` is a *visual shell, not an authorization boundary*. Every page, route handler and server action calls `requireAdmin()` itself. Verified: every `page.tsx` under `/admin` except the login page, every `route.ts`, and every `"use server"` action.

**Login hardening** (`app/admin/login/actions.ts`): one message for every failure (`"Invalid email or password."`), and `verifyPassword` always runs — against a real throwaway bcrypt hash `DUMMY_HASH` when no admin matched — so a missing account and a wrong password take the same time.

> **Known gap:** there is no rate limiting on admin login or on the candidate sync endpoint.

## 7. Candidate flow

### 7.1 Start — `/exam/start` → `lib/exam/start-exam.ts`

Two fields only: **email** and **mobile**. (No name field — the candidate's real name comes from the `Candidate` row.)

Order of decisions, all server-side:

1. Validate email (required, ≤ 320, pattern) and mobile (required).
2. `normalizeMobile` — the *same* function the Google Form sync uses.
3. **Re-check `isOpen` immediately before the write**, not at render: an admin may close the exam while the candidate sits on the form. The page is `force-dynamic` so a prerender can never keep offering a closed exam.
4. Find the candidate by **mobile OR email** (`findFirst`, `orderBy registeredAt asc`, email compared `mode: "insensitive"`). A mobile that fails normalization contributes no clause rather than an `undefined` filter that would match every row.
5. **Eligibility gate:** a `CandidateExam` row must exist for `(candidateId, SETTINGS_ID)` → otherwise `not_selected`.
6. Existing attempt: `in_progress` → **resume** (same attempt, `startedAt` untouched); anything terminal → `completed`.
7. Otherwise create the attempt, then `withPaper(...)`.

> ⚠️ **README drift:** the README states the mobile number alone is the eligibility key. The code matches on **mobile *or* email**, which the source comments acknowledge is deliberately weaker: whoever knows either a selected candidate's number or their email can start that candidate's exam. There is no OTP behind it — the `CandidateExam` selection list is the only real gate.

`StartOutcome` = `started{resumed} | closed | ineligible | not_selected | completed | invalid{errors} | failed{reason}`.

`not_selected` is kept distinct from `ineligible` because the brief requires the UI to tell them apart, even though that reveals slightly more.

**Empty-attempt cleanup.** An attempt row is created before its paper is drawn, so a generation failure used to leave an `in_progress` attempt with zero questions — worse than no attempt, because the candidate's next start *resumes* it and is handed the same empty paper. `discardEmptyAttempt` deletes it, guarded on still-in-progress and still-empty. **Only an attempt this call created is ever discarded**; a resumed one is never deleted.

**Race:** a double-click races two creates; the partial unique index rejects the loser, which then resumes the winner's attempt rather than erroring.

`FailureReason` (`lib/exam/failure-reason.ts`) splits failures into two candidate-facing categories, because they call for opposite actions:
- `not_ready` — `NO_ACTIVE_SECTIONS`, `SECTION_INSUFFICIENT_QUESTIONS`, `LESSON_SECTION_INSUFFICIENT_GROUPS`, `PAPER_INVARIANT_FAILED`. Retrying cannot help; fetch a supervisor.
- `error` — `ATTEMPT_NOT_FOUND`, `ATTEMPT_NOT_IN_PROGRESS`. Retrying may well work.

Which section is short, and by how much, stays in the server log — the bank's composition is the one thing an exam-taker must not see.

### 7.2 Paper generation — `lib/exam/paper-generation.ts`

Drawn **once**, at start, and never redrawn — not on refresh, resume, a changed bank, or a changed mix. The `attempt_questions` rows *are* the paper.

- **Eligibility:** `isActive: true` only. (The `status = ready` requirement was removed in migration `20260911000000`.)
- **Pool:** read via `getQuestionPool()`, a 30-second per-process cache (see §7.3).
- **Active sections:** `getActiveSectionCodes()` is read **once, here** — the result is baked into the rows. Toggling a section afterwards has zero effect on papers already drawn.
- **Difficulty:** `allocateDifficultyCounts` uses **largest-remainder** rounding — floor each share, hand leftovers to the largest fractional parts, ties in easy/medium/hard order. Naive rounding overshoots (40/40/20 of 4 is 1.6/1.6/0.8 → 2/2/1). If the bank is short on a difficulty, the allocation clamps and redistributes the shortfall to difficulties with spare capacity, ordered by remaining room so the result stays as close to target as possible. Returns `null` only when there are genuinely too few questions overall.
- **Learn-and-Apply:** drawn as **whole lessons**. Groups with fewer than 3 eligible questions are excluded entirely. Every complete group's difficulty profile is scored against the target, the closest *pair* wins (chosen at random among equally close pairs), and each group's three questions stay together and in authored order. Fewer than 2 complete groups fails generation.
- **Option shuffling:** Fisher-Yates over `crypto.randomInt` (tests inject a deterministic `rand`). `correct` **keeps its original key** and is never rewritten to a shuffled position.
- **Snapshot:** question text, code block, all four options, `correct`, explanation, lesson text/group, marks and `scored` are copied at draw time. `verifyCode` is never loaded. `sectionCode` is deliberately *not* stored — the snapshot records the ordinal.
- **Validation:** `validateGeneratedPaper(rows, activeSections)` checks question count, total marks, duplicate questions, gapless 1..N display order, section blocks and order, lesson-group completeness and contiguity, and option permutations. `activeSections` is a **required** parameter (defaulting it to the static blueprint made a retroactive comparison the implicit behaviour). Nothing reaches the database unvalidated.
- **Concurrency:** one transaction. Two simultaneous requests cannot produce two papers — the unique constraints on `(attempt_id, display_order)` and `(attempt_id, question_id)` reject the loser, whose **P2002** is caught and answered with the winner's paper rather than an error.

### 7.3 Question pool cache — `lib/exam/question-pool.ts`

`POOL_TTL_MS = 30_000`, held on `globalThis`, with in-flight request coalescing so a cold-cache start spike issues **one** query rather than one per candidate.

Safe because: the drawn paper is snapshotted (a stale pool can only influence which questions a *new* paper draws from); every paper is validated before it is written; staleness is bounded and benign (an activation takes effect in about the time it takes to navigate back); and instances need not agree, since papers are per-candidate and independently randomized anyway.

`invalidateQuestionPool()` drops this process's copy after an admin edit. It is explicitly **not** distributed invalidation, and correctness never depends on it being called.

### 7.4 The exam screen — `app/exam/`

`app/exam/page.tsx` is `force-dynamic`. It resolves the attempt from the cookie, redirects to `/exam/start` if absent, short-circuits to `TerminationScreen`/`CompletionScreen` for a non-`in_progress` attempt, then loads paper + timing + answers + progress in parallel and renders `ExamShell`.

**What the browser receives** (`lib/exam/candidate-paper.ts`): the server names every field explicitly rather than spreading the row, so anything added to the snapshot later is withheld by default. **`correct`, `explanation` and `verifyCode` never leave the server.** `lessonGroup` is replaced by an opaque 1-based `lessonIndex` — the real authoring identifier is used to build the map and then discarded. `attemptRef` is the attempt uuid's first block, uppercased, so a candidate can quote their sitting without the full id on screen.

**Rendering.** One question at a time, from the snapshot; the bank is never read. Options appear in stored `shuffledOptionOrder` and keep their **original key**, so selecting the first displayed option records `c` if C is displayed first. Nothing is shuffled at render time. Code blocks render through PrismAsyncLight with only `javascript` registered. Lesson text renders as plain text, never markup, and repeats above each of a group's three questions (a candidate may jump straight to any of them).

**Question palette.** Three states — `answered` (from the `Answer` row), `skipped` (visited, unanswered), `unseen` — plus a `current` ring. Every state differs by fill, border weight *and* text weight, not hue alone, and each button's `aria-label` carries the state in words. **There is no "mark for review"** — it is not in the requirements or the data model. From `lg` up the palette is a sticky sidebar; below, the same markup collapses into a native `<details>` (keyboard-operable and announced as expandable, needing no focus trap or portal).

**Timer** (`exam-timer-display.tsx` + `lib/exam/exam-timer.ts`). The deadline is always `startedAt + durationMinutes`, computed server-side. On mount the client measures `skew = serverNow - Date.now()` and counts down from the *difference*, so **changing the machine clock shifts both sides equally and buys no time**. A 1s interval drives the display; a **300s** resync calls `fetchTiming()`. Five minutes rather than thirty seconds because at 30s the poll was ~150 requests per candidate per sitting and, at 3 queries each, roughly **40% of all database traffic the exam produced** — and the deadline is a constant the countdown does not need re-derived. It is reduced rather than removed because the poll does one thing the countdown cannot: notice the attempt has stopped being live. `StopReason` distinguishes `time-up` (deadline; auto-submits) from `unavailable` (session no longer resolves), because saying "time is up" beside a timer reading an hour is a statement the candidate can see is false. The visible digits are `role="timer"` and *not* a live region; a separate `sr-only` span announces only at five minutes and each whole minute below it.

**Auto-save** (`use-autosave.ts`). No Save button. MCQ saves immediately; free text debounces **600 ms**; anything pending is flushed on `pagehide`. Each question carries **its own sequence number** — a response whose sequence is no longer current is discarded, so a slow save of "B" landing after a fast save of "C" cannot claim B was stored. `flush()` races outstanding saves against a **30 s** timeout, because a Server Action on a dropped connection does not reject promptly; on timeout it clears `inFlight` so one abandoned request cannot poison every later flush, and resolves `false` — the honest answer being that the saves could not be *confirmed*. The header shows *Saving… / Saved / Not saved* and never claims a save that did not happen.

**Server-side save rules** (`lib/exam/save-answer.ts`). Every save re-derives the attempt from the cookie, confirms the question belongs to *that* attempt, confirms the attempt is in progress and the deadline has not passed, and decides from the **stored section** whether the question takes an option or prose — no client flag is trusted. `MAX_TEXT_ANSWER = 5000`. Free text is trimmed only at the outer edges, so deliberate line breaks and indentation survive. `isCorrect` and `marksAwarded` are never written here; scoring owns them.

**Progress recovery** (`lib/exam/exam-progress.ts`). Two guarded writes in one transaction, neither a read-modify-write: `visitedAt` is set **only where it is still null** (set-once, so it needs no sequence of its own), and the position is set **only where the stored `currentPositionSeq` is lower**, enforced in SQL. Returns `stale` rather than `saved` when a newer report already won.

**Resume.** Refresh, navigate away, or reopen — same attempt, same paper, same option order, same answers, timer continuing from the original `startedAt`. Two tabs share one attempt and write to the same rows. If the cookie is gone, the candidate re-enters through `/exam/start` and lands back on the same attempt.

**Submission** (`lib/exam/finalize-attempt.ts`). The confirmation dialog counts answered/unanswered from **stored** answers, only after any pending save has been flushed, and says so plainly if a save failed rather than showing a count. An attempt ends **exactly once**: the write is `updateMany` guarded on `status = in_progress`, so a repeated click, a retry, or a manual submit racing the auto-submit all find the row settled and return the state that won. **The server decides which terminal state gets written, from its own clock** — a manual submit arriving after the deadline records `auto_submitted`. The `intent` argument only says which button was pressed.

**Auto-submit.** At zero the page asks the server to finalize; the server honours it **only if its own clock agrees** (`intent === "automatic" && !expired` → `not-expired`), and the page keeps asking every 2s. A closed browser cannot make that request — what actually protects the exam is that once `startedAt + duration` passes, writes are refused everywhere. An abandoned attempt simply stays `in_progress` until something touches it; finalizing those would need a scheduled job this deployment does not have.

**After submission.** The completion screen shows **no score, marks, answers or explanations**, and a finalized attempt never reopens.

### 7.5 Anti-cheating — `lib/exam/anti-cheating/` + `app/exam/anti-cheating-monitor.tsx`

Explicitly **not a security boundary** — every check is defeatable with OS-level access. It catches casual attempts and gives the server something to count; **the server alone decides whether an attempt ends.**

**Reported** (spends the violation budget): `TAB_SWITCH` (visibilitychange → hidden), `WINDOW_BLUR`, `FULLSCREEN_EXIT`, `DEVTOOLS` (window-dimension heuristic), `PAGE_LEAVE` (beforeunload).

**Blocked but deliberately not reported** — these are the common *accidental* triggers, and counting them would exhaust the warning budget on harmless behaviour; silently preventing the action is the real deterrent: context menu, copy/cut/paste (cut and drag are skipped inside form fields so free text stays usable), drop, middle-click, print, and the keyboard set `F5`/`Ctrl+R`, `F12`, `Ctrl/Cmd+Shift+{I,J,C}`, `Ctrl/Cmd+U`, `Ctrl/Cmd+P`, `Ctrl/Cmd+S`, `Ctrl/Cmd+F`, `Ctrl/Cmd+Tab`, and `Ctrl/Cmd+{C,X,V,A}` **only outside form fields**. Plain typing, arrows, Tab, Enter and Space are never touched.

**Two-layer dedup** (`dedup.ts`, pure and unit-tested). One physical action fires several browser events — a tab switch *is* a blur; opening DevTools can trigger both a shortcut and a resize heuristic. So: any event within **`BURST_WINDOW_MS = 800`** of the previous one is the same incident **regardless of type**, and additionally one canonical type is suppressed for **`DEDUP_WINDOW_MS = 1500`** so its own repeats do not restart the count. `DEDUP_GROUP` folds `WINDOW_BLUR → TAB_SWITCH`.

**DevTools heuristic:** `THRESHOLD_PX = 160` on `outer − inner` dimensions, debounced to once per **30 s**. Deliberately soft — a large gap is equally explained by zoom or OS scaling — so it never terminates on its own.

**Fullscreen:** best-effort `requestFullscreen()` on mount. On exit, report then attempt one quiet re-entry; because `requestFullscreen` only succeeds synchronously from a user gesture (which a `fullscreenchange` handler lacks), a rejection raises a "Return to fullscreen" `alertdialog` whose button supplies a fresh gesture.

**Server side** (`service.ts`): the attempt always comes from the cookie. In one transaction, count existing rows, create the violation with `sequence = count + 1`, and increment `violationCount` via `updateMany` **guarded on `status = in_progress`** — so a violation racing finalization cannot resurrect a count on a finished attempt. Then `reachesLimit(count, limit)` (`count >= limit`) either returns a warning or calls `terminateForViolation`, which is the same guarded conditional update. **A terminated attempt is never scored.** A network failure client-side is **not retried** — retrying a stale event under a different dedup window risks double-counting, and a missed event is not a correctness problem.

### 7.6 Scoring — `lib/exam/scoring.ts`

Runs entirely server-side. Nothing about it is reachable from the candidate browser.

**When.** `finalizeAttempt` calls it immediately after the attempt reaches a terminal state, so manual and automatic submissions score identically. Only `submitted`/`auto_submitted` can be scored.

Scoring is **deliberately not part of finalization's atomic write**. The attempt is already terminal when scoring starts, and a failure is logged and swallowed rather than rolled back — reverting would hand a submitted candidate their exam back. A failure leaves the attempt finalized with `scoredAt` null, which is exactly what the retry picks up.

**Rules.**
- **Snapshot-based.** `correct`, `marks`, `section` and `scored` all come from `AttemptQuestion`. The live `Question` row is never read.
- **No negative marking.** Wrong, missing or malformed answers are worth 0, never less.
- **Unanswered** scores 0 with `isCorrect = false`, keeping `selectedOption = null` so an admin can still distinguish it from a wrong answer.
- **Invalid answers** (outside `a`–`d`) are treated as unanswered.
- **Unscored questions** keep `isCorrect = null` — *not* `false`, which would claim the candidate got it wrong.
- **Validated against the paper's own recorded sections**, never today's blueprint, so a paper drawn under a different exam shape is scored correctly on its own terms.

**Arithmetic.** All sums run in **integer hundredths** (`SCALE = 100`) and convert to a fixed 2-decimal string only at the edges, so a section of 1.5-mark questions totals exactly `12.00` rather than `11.999999999999998`.

**Persistence.** One set-based `INSERT … SELECT FROM unnest(...) ON CONFLICT ("attempt_question_id") DO UPDATE` covering the whole paper — a per-row upsert loop kept an interactive transaction open past its timeout when several callers scored at once. The `ON CONFLICT` clause updates **only** `is_correct` and `marks_awarded`; a candidate's `selected_option` and `text_answer` are never touched. A section the paper never drew writes `null`, not `"0.00"` — a fabricated zero is indistinguishable from a genuine zero.

**Failure.** A paper that cannot produce a valid score (wrong count, section over its maximum, unknown section, total out of range) is **refused**, nothing is written, and the problems are logged. The result is never clamped into range: an impossible score is a data problem for an admin, not a number to round.

**Idempotency.** Each run recomputes everything from stored state, so re-running is a no-op rather than a doubling.

### 7.7 Scoring recovery — `lib/exam/pending-scoring.ts` + `/api/internal/scoring-retry`

Under load this stopped being hypothetical: **16 of 50 simultaneous submissions ended with no score** because scoring's transaction could not acquire a connection in time. The attempt and every answer were intact; only the computed result was missing, and nothing ever went back for it.

- `findPendingScoring(limit)` / `countPendingScoring()` — the plain definition of the problem: finished, but `scoredAt` null.
- `backfillPendingScoring(limit = 20)` — processes attempts **one at a time**, deliberately: this runs *because* the database was under pressure, and firing a hundred concurrent scoring transactions at a pool that just failed to serve them would reproduce the original failure.
- **Advisory lock.** `pg_try_advisory_xact_lock(8140231)` — **transaction-scoped, not session-scoped**, and that distinction is load-bearing: the app connects through Supavisor in transaction mode, which hands out a different backend per transaction, so a session-level lock is taken on one backend and looked for on another and provides no mutual exclusion at all. Measured: through the pooled URL two concurrent callers *both* acquired a session lock, while the transaction-scoped form correctly granted one and refused the other. `try` rather than blocking, so a second run declines immediately; declining is reported (`skippedConcurrent`), not thrown.
- **`BATCH_LIMIT = 20`.** The batch sits inside one transaction and must finish inside the 15s timeout; scoring one attempt is ~5 round trips at ~80–110 ms ≈ 0.4s, so 20 ≈ 8s (safe) and 50 ≈ 19s (would abort and score nothing). A backlog drains over several invocations.
- Driven externally rather than by an in-process timer, because a timer would be process-local: every instance would run its own copy, and a deployment with no instance running would silently stop repairing anything.

### Query-parameter contracts

Every parser maps unrecognised input to a safe default, so **nothing from a query string ever reaches Prisma as a field name or direction**.

**`/admin/attempts`** — `q` (≤200), `status` ∈ `in_progress|submitted|auto_submitted|terminated`, `scoring` ∈ `scored|pending`, `candidate` (≤100, resolved against the DB — an unknown id yields an empty result with `unknownCandidate: true` rather than silently dropping the filter), `sort` ∈ the six `SortKey`s (default `newest`), `page` ≥1, `pageSize` ∈ `10|25|50|100`.

> `sort` is validated with **`Object.hasOwn(SORTS, raw)`, deliberately not `in`** — `in` walks the prototype chain, so `__proto__` and `constructor` would pass the allowlist and then index to `undefined`.

"Scoring pending" means finalized-but-unscored; an in-progress attempt is *not* pending and is excluded.

**`/admin/candidates`** — `q` (≤200, matching **21 fields** including every profile column), `selected` ∈ `all|selected|not_selected`, `page`, `pageSize`. Fixed ordering `[{registeredAt: desc}, {id: asc}]`; no sort param.

**`/admin/questions`** — `search` (≤200; id/question/topic), `section`, `difficulty`, `active`, `scored`, `readiness` ∈ `ready-to-activate|not-ready`, paging. **A non-empty `search` overrides every other filter**, so searching a known id cannot be hidden by a leftover filter. `readiness` is derived per row rather than a SQL predicate, so that path reads the matching set in full and pages in memory.

### Individual result — `lib/admin/attempt-result.ts`

Review-only: no edit, override, rescore, reopen or delete control anywhere.

| Attempt state | What is shown |
|---|---|
| `in_progress` | Metadata only. **No score, no correct answers, no explanations, no review.** |
| finalized, `scoredAt` null | "Scoring Pending". Nothing is scored by opening the page. |
| finalized and scored | Full result: total, section breakdown, every question |

The in-progress case returns **before any snapshot row is loaded**, so the answer key cannot reach the page while a supervised exam is running.

Everything historical comes from the `AttemptQuestion` snapshot; the live `Question` table is never read. Options are reconstructed from `shuffledOptionOrder` so the admin sees the paper exactly as the candidate did, and the letter shown is the original snapshot key. States are distinguished rather than collapsed: **Correct / Wrong / Unanswered / Unscored** — an unanswered question is never labelled wrong. `topic` is not shown because it is not part of the snapshot, and reading it live would break historical integrity for one label.

An ordinal with no blueprint entry becomes a synthetic "Retired section" row — shown rather than dropped. Each attempt's maximum is its **own paper's** `_sum(marks)` where `scored: true`, never a blueprint constant, because sections toggle on and off and two attempts legitimately have different maximums.

### Exports — `lib/admin/sheet-export.ts` + `xlsx-export.ts`

Both are **XLSX**, generated straight into the HTTP response — nothing is written to disk, uploaded, or served from a public URL, and no content is ever logged.

> ⚠️ **README drift:** the README describes these as CSV exports. They were converted to Excel in commit `d97e8bf`. CSV carries no formatting, so Excel opened each column at default width and a long question or code block was unreadable until autofitted by hand.

**Summary** (`/admin/attempts/export`, sheet "Attempts", **28 columns**):

```
attempt_id, candidate_name, candidate_email, candidate_mobile,
entered_name, entered_email, status, started_at, submitted_at, scored_at,
total_score, max_score,
section_3_score, section_3_max, section_5_score, section_5_max,
section_7_score, section_7_max, section_1_score, section_1_max,
section_2_score, section_2_max, section_4_score, section_4_max,
section_6_score, section_6_max, section_8_score, section_8_max
```

Section pairs follow `SECTION_BLUEPRINT` array order; names keep the **historical ordinals** so files produced before and after the section-code change line up. Ordinal 8 is retired and exports whatever was stored, else blank. Filters are honoured (parsed by the same `parseAttemptFilters` the page uses); **paging is deliberately ignored** — the export covers the whole filtered set.

**Detail** (`/admin/attempts/[id]/export`, sheet "Result", **29 columns**):

```
attempt_id, candidate_name, candidate_email, candidate_mobile, attempt_status,
started_at, submitted_at, scored_at, question_number, section, section_name,
question_text, code_block, option_a, option_b, option_c, option_d,
displayed_option_order, candidate_answer, candidate_answer_text,
correct_answer, correct_answer_text, result, marks_awarded, max_marks,
explanation, lesson_group, lesson_text, scored
```

Refuses an in-progress attempt (**409**) as well as hiding the button: those rows carry the correct answers and explanations, and handing them over during a supervised sitting would leak the answer key. 404 for an unknown attempt.

**Cross-cutting export rules:**
- **Blank ≠ zero.** A score cell is empty unless the attempt is both finalized and scored — `0.00` would read as "scored zero".
- **Formula injection is neutralised on every cell.** `/^[=+\-@\t\r]/` gets a `'` prefix. Applied to XLSX too, since Excel executes regardless of container. A genuinely negative number is quoted as well: there is no way to distinguish `-5` from `-1+1` without parsing, and a visible quote is far cheaper than executing a formula from a candidate-supplied name.
- Filenames carry a date (and the attempt id for detail) but **never** a name, email or mobile — filenames land in download histories.
- `Cache-Control: no-store` on all three routes.
- `buildWorkbook` sets column widths, `!freeze = "A2"` and an autofilter. A `ponytail:` comment notes that cell styling (`cell.s`) is silently dropped by the community `xlsx` build; exceljs would be needed for real styling.

### Question bank

**Two states only:** `isActive` true or false. The three-stage `draft/review/ready` workflow was removed in migration `20260911000000`; paper generation draws on `isActive` alone.

**Import never activates.** Every imported question is created `isActive: false`, and `isActive`/`scored` are excluded from the update branch — so re-importing cannot reactivate a question an admin deactivated, nor deactivate one they activated. Activation is a separate, deliberate administrative act.

**Activation gate** (`activation-readiness.ts`) is the single server-side authority, returning **every** failing reason rather than the first:

| Reason | Message |
|---|---|
| `MISSING_QUESTION_TEXT` | Question text is empty |
| `MISSING_OPTION` | One or more options are empty |
| `INVALID_CORRECT_ANSWER` | Correct answer is not one of A–D |
| `INVALID_MARKS` | Marks are not a valid storable value |
| `INVALID_DIFFICULTY` | Difficulty is not easy, medium or hard |
| `INVALID_SECTION` | Section is not one of the seven active section codes |
| `MISSING_LESSON_TEXT` | Learn-and-Apply questions must carry lesson text |
| `INVALID_LESSON_GROUP` | Learn-and-Apply questions must belong to a lesson group |

The batch check adds the one rule a single row cannot answer: an LRN question whose lesson group does not hold exactly 3 questions **in the database** (not within the selection — activating one question of a lesson is legitimate when the other two are already active).

Deliberately **not** checked: whether a question is *good*, and whether its marks match the blueprint. The source file is the truth for what a question is worth; a mismatch is *surfaced* by the readiness summary, never corrected.

**Bulk activation** (`MAX_BULK_IDS = 1000`) is **all-or-nothing** — a partly-applied batch would leave the admin unsure which half took effect. Only the ids are trusted from the browser, and only as identifiers: every field activation depends on is **re-read from the database**. Deactivation skips the readiness check entirely (removing a question from the pool is always safe; refusing would strand a bad question in play).

**Deactivating never deletes.** There is no question-deletion operation anywhere in the codebase, and the editor's source comment says none may be added. Editing or deactivating cannot touch historical attempts, which carry their own snapshot.

## 9. Import pipelines

Three independent pipelines. Uniform row numbering: **header is row 1, first data row is 2**, header errors at row 1, file-level errors at row 0.

### Two different philosophies, deliberately

| | Question bank | Candidate importers |
|---|---|---|
| Header matching | Normalized (`trim().toLowerCase().replace(/\s+/g,"_")`); extra columns **ignored** | Identity headers matched by **exact, case-sensitive text**; the live import treats any unmapped column as **fatal** |
| Failure model | **All-or-nothing** across every file, one transaction for the whole batch | Header-fatal / **row-partial**, one transaction **per row**, `CONCURRENCY = 10` |

The candidate importers use exact matching because the live sheet has two email columns one case-change apart — see §9.2.

### 9.1 Question bank — `lib/question-bank/`

**15 source columns**, any order, extra columns ignored:

```
id, section, topic, difficulty, question, code_block, verify_code,
option_a, option_b, option_c, option_d, correct, explanation,
lesson_text, marks
```

Optional (may be blank): `code_block`, `verify_code`, `explanation`, `lesson_text`. **`status` is deliberately not a column**, and **`lesson_group` is derived, not read.**

> ⚠️ **README drift:** the README documents a 19-column contract including `scored`, `ai_verified`, `trainer_verified` and `status`. The live contract is the 15 above.

- **Enums** (case-insensitive after trim; unknown = error, never a default): `difficulty` ∈ easy/medium/hard, `correct` ∈ a/b/c/d, `section` via `resolveSectionCode`.
- **Marks** stay a **string end-to-end**, never parsed to a float before Prisma: `/^\d+(\.\d+)?$/`, ≤2 decimal places, ≤ `99.99` (matching `Decimal(4,2)`).
- **Limits:** `MAX_ID_LENGTH = 64`, `MAX_TOPIC_LENGTH = 200`, accepts `.csv`, `.xls`, `.xlsx`.
- **Cross-field:** LRN questions must carry lesson text.
- **Duplicate ids** are rejected **across the entire import**, not per file, naming where the id was first seen.
- **Non-question sheets** in a workbook are *skipped and reported*, not failed — a sheet qualifies if its headers contain both `id` and `section`. The line is drawn there on purpose: a sheet with `id`+`section` but missing `marks` is a real question sheet with a real mistake and must be reported. **The test is the headers, never the sheet name.**
- **Lesson grouping** buckets LRN rows by identical lesson text into internal ids `LRN-LESSON-{n}`. Group size is deliberately *not* enforced here — an incomplete group is a data problem visible in the bank, and paper generation refuses to draw it.
- **Write:** one transaction for the whole batch (`timeout: 120_000`), chunks of 100, upsert on the primary key.
- **Preview round-trip:** the validated batch is handed to the browser so confirm need not re-upload. What comes back is untrusted — `verifyRows` rebuilds every row **field by field, never spread**, and returns `null` on any violation (a failure there is not an authoring mistake, so the UI just asks for the files again).
- CSV is parsed **without `header: true`** so duplicate headers survive to be reported rather than silently collapsing into one key.

### 9.2 Live candidate sheet — `lib/candidate-import/`

**The email-header trap.** The live sheet has two email columns whose real headers differ by **one letter's case**:

- `"Email address"` (lowercase) — **explicitly ignored**
- `"Email Address2"` — the canonical candidate email

Both are matched by **exact, case-sensitive `===`**, never through a normalizer. `CANONICAL_EMAIL_HEADER` is set to `"Email Address2"` on explicit business instruction **even though the copy of the sheet in this repo (`untill tow 101.xlsx`) spells its second email column `"Email Address"` with no `2`**. If a real upload truly lacks the `2`, header validation **rejects the file** as missing the canonical email column rather than silently falling back to the wrong one. Full record in `docs/candidate-import-field-mapping.md` — that document and `csv-contract.ts` are mirrors; change one, update the other.

23 normalized columns plus the exact-text email. **Required** (column present *and* non-blank per row): `timestamp`, `full_name`, `mobile_number_(whatsapp)`, `Email Address2`. The other 20 are optional both as columns and as values.

- **Any unrecognised column is fatal** (unlike the question bank) — silently dropping one would violate the "every field must be stored" requirement.
- Limits: `.csv`/`.xlsx` only (**no `.xls`**), 10 MB, 20,000 rows, name ≤200, email ≤320, free text ≤20,000.
- Blank cells become `null`, never `""`, so the write layer can distinguish "blank in the sheet" from a real empty string.
- **Dates** use the platform parser (`M/D/YYYY H:mm:ss` and `M/D/YY`, the formats the sheet verifiably uses). An unparseable `date_of_birth` leaves the field null rather than failing the row; an unparseable `timestamp` fails the row.
- **One merge rule:** `"Have you built any project?"` has no column of its own, so it is folded into `projectInfo` as `"{builtProject}: {projectDescription}"` rather than discarded.
- **`toWriteData` omits null optional fields entirely**, so an incomplete live export can never erase a value already on file.
- **Writes `Candidate` only** — never `CandidateExam`, `Attempt` or `ExamSession`.

**Matching** (`match-candidate.ts`, pure and DB-free) — evaluated in order:
1. Email matches >1 candidate → conflict
2. Mobile matches >1 → conflict
3. Email and mobile match *different* candidates → identity conflict
4. `emailMatch ?? mobileMatch` → update (**email first**, mobile second, covering a candidate whose email changed between submissions)
5. Neither → create

**Known accepted limitation:** two rows in the same file resolving to "create" for the same new email/mobile, landing in the same concurrent chunk, can both read "no match" and both insert — there is no unique constraint to stop it. Not addressed because the real sheet has zero duplicate emails, and a genuine duplicate is an identity question an admin should see, not one the import should collapse by serializing every write.

### 9.3 Selected candidates — `lib/candidate-selection-import/`

Marks existing candidates as selected. **Never creates or updates a `Candidate`** — only `CandidateExam`.

Three exact-text headers: `Email Address2` (required, primary key), `Mobile Number (WhatsApp)` (required column, fallback key), `Full Name` (optional, **error reporting only** — never identity, never written). `Email address` is ignored. Any other column is simply ignored.

- **An invalid email does not fail the row** — it becomes `null` and a valid mobile can still identify the candidate. Only a genuinely unusable *pair* fails.
- Idempotent: an existing `CandidateExam` counts as `alreadySelected`, and a **P2002** race from two admins importing the same file concurrently is also counted as `alreadySelected` (the row *is* selected, just not by this transaction) rather than failed.
- `examId` is verified to name a real `ExamSetting` **before anything is written**, so a typo can never produce orphan rows. It is an explicit parameter rather than a hardcoded constant — the admin action decides which exam a selection applies to, which is the single place to change for real multi-exam support.

**Eligibility enforcement:** `CandidateExam` existence is the actual gate on starting the exam (§7.1). A candidate already mid-exam when this shipped is **not** automatically exempt — their next resume is rejected the same as a fresh start.

**Deselection:** the import can only ever *grant* eligibility. The one place that can remove a `CandidateExam` row is the admin `setCandidateSelection(id, false)` toggle, and that is a real, permanent removal — a candidate with an `in_progress` attempt will be rejected on resume, deliberately not special-cased.

### 9.4 Identity normalization — `lib/integrations/candidate-payload.ts`

**One `normalizeMobile` shared by every candidate path** (CSV import, selection import, Google Form sync, admin manual add, exam start) so no route can accept a number another would reject.

```
MOBILE_PATTERN = /^[6-9]\d{9}$/     // Indian 10-digit
```

Strips `[\s\-().]` only. If the cleaned value already matches, return it. **If the cleaned length is ≤10 and it did not match → `null`** — this guard is the important subtlety: a genuine 10-digit number may legitimately begin `91` (e.g. `9157571942`), so the national prefix is stripped **only** when the number is already 11+ digits. Never rewrites a number into a different one.

`EMAIL_PATTERN = /^[^\s@]+@[^\s@]+\.[^\s@]+$/`, `MAX_NAME = 200`, `MAX_EMAIL = 320`, `MAX_RESPONSE_ID = 128`.

## 10. API routes

### `POST /api/integrations/candidates`

Google Form → CloudUS sync. Auth: `Authorization: Bearer <GOOGLE_APPS_SCRIPT_SECRET>`, compared with `timingSafeEqual` after an explicit length check (it throws on a length mismatch).

Body: `{ google_form_response_id, name, email, mobile }` — all four required.

| Status | Meaning |
|---|---|
| 201 | Candidate created |
| 200 | Existing candidate updated (incl. a resolved race) |
| 400 | Invalid JSON or failed validation |
| 401 | Missing/wrong bearer |
| 500 | Secret not configured, or a database failure |

Upserts on the unique `googleFormResponseId`, so Apps Script may safely retry. A **P2002** from two simultaneous requests is caught and re-applied as an update. **If the secret is unset the endpoint refuses every request (500) rather than accepting unauthenticated writes.** Error logs record only `error.name`, since a Prisma error may carry the connection string.

### `/api/internal/scoring-retry`

Same bearer scheme against `SCORING_RETRY_SECRET`. `GET` → `{ success, pending }` for monitoring (zero is healthy; a number that does not fall across successive runs means scoring is failing for a reason a retry cannot fix). `POST` → runs the backfill, returns `{ examined, scored, skipped, failed, remaining }`. Same refuse-to-serve-without-a-secret rule.

### `GET /api/version`

**No auth — public on purpose**, so a deploy can be confirmed without an AWS console login. Returns `{ commit, branch, buildId, builtAt }` with `Cache-Control: no-store` and `X-Robots-Tag: noindex, nofollow`. Amplify's `AWS_COMMIT_ID`/`AWS_JOB_ID`/`AWS_BRANCH` exist only while the build container runs, so `next.config.ts` copies them into `NEXT_PUBLIC_*` vars that Next inlines into the bundle — what this reports is baked into the artifact and cannot drift from it. Both `undefined` and `""` map to `"unknown"`, because Next inlines `""` for an absent var and a blank could otherwise read as stale.

## 11. UI system

### Two scoped themes, light only

`app/globals.css` (322 lines, Tailwind v4 `@theme`) defines two parallel token sets. Every candidate surface renders inside `.cloudus-exam`; every admin surface inside `.cloudus-admin`, so neither can reach the other or the public landing page.

**Light mode only is a product decision**, not an oversight: the dark block was *deleted* rather than overridden. It was never designed (mechanical inversion), doubles the review surface of every page, is never asked for by the requirements, and the usage context is a fixed office desktop under constant lighting. Status colours in particular need different values in dark mode to stay accessible and nobody has specified them.

Exam tokens are prefixed `exam-` so they cannot collide. Key values: page `#f4f6f9`, surface `#ffffff`, ink `#10151c` (darker than admin — long-form reading), primary `#1f5fbf`, focus `#0b3d91` (**deliberately not brand blue**, so the ring stays visible against a brand-tinted selected option). Layout tokens: palette 312px, header 97px, reading measure 76ch.

The focus colour is **spelled literally** in the `:focus-visible` rule, because Tailwind v4 registers `@theme` colours with `@property … inherits: false`, so `var(--color-exam-focus)` resolves to its initial value on a descendant.

Admin palette (from `docs/design/admin-panel-design-plan.md`): `bg.page #F7F8FA`, `text.primary #14181F` (16.1:1), `primary.base #1F5FBF` (5.4:1), status `success #166534`, `warning #8A5300`, `danger #A81E1E`, `info #1A4FA0`, `neutral #4A5261`. **Exam Closed uses `neutral`, not `danger`** — closed is the safe default state, not an error. Section 8 "Unscored" uses `neutral`, never green/red, so it cannot imply correctness.

Shared breakpoints: `sm 480px` (**overriding Tailwind's default 640**), `md 768`, `lg 1024`, `xl 1440`. Admin layout tokens: sidebar 240px, rail 56px, topbar 56px, drawer 280px. Each scope has its own `:focus-visible` rule, its own tabular-numerals helper (`.tabular` / `.exam-tabular`) and its own `prefers-reduced-motion` block. Keyframes: `toast-in`, `drawer-in`, `loader-sweep`.

### Design rules the plans bind (and the code enforces)

- **Typography:** Geist Sans + Geist Mono, **three weights only — 400/500/600, no 700+, no italics, never below 12px**. All numeric columns `tabular-nums`. One `<h1>` per page.
- **Spacing:** 4px base scale `0 4 8 12 16 20 24 32 40 48 64` — never a value outside it. **Radius** 4/6/8/full, nothing larger except pills. **Cards get no shadow**; structure comes from borders. Shadows are only for sticky headers, dropdowns, popovers and modals.
- **Motion:** nothing above 200ms; focus rings are instant (a delayed focus ring feels broken). No page transitions, entrance animations, number count-ups, parallax or hover-lift. `prefers-reduced-motion` changes *how* a toast appears, **never how long it stays** — shortening its life would cost information.
- **Toast vs Alert is a hard division.** Toast = "that worked, carry on" (transient, never the only place important information appears). Alert = "read this before continuing" (persistent, in the content flow). **An error the admin must act on is never toast-only.** Toasts are always *derived from the Server Action's returned state*, never a parallel imperative `toast()` — otherwise a success message can fire without the mutation having succeeded. The toast system is hand-rolled (no `sonner`/`react-hot-toast`): a provider, context, timer and portal under 150 lines, and the a11y rules need hand-verification either way.
- **Responsive:** the original "office PCs only" requirement was explicitly lifted. Tables show full columns ≥1024, *drop* low-priority columns (never squeeze) at 768–1023, and become stacked record cards below 768 while keeping table semantics for assistive tech. Import previews and the blueprint table stay horizontally scrolling at every width. Hard rules: the page body never scrolls horizontally, **no functionality is removed at any breakpoint**, no separate mobile routes, 44×44px minimum touch target below `md`, no hover-only affordances.
- **Icons:** `lucide-react`, ~20 of them, always `currentColor`. Icons support labels; they replace them only in the collapsed rail and table action buttons, both of which require `aria-label` + tooltip.
- **Code-level conventions:** every component opens with a `///` comment explaining *why* it exists and what it refuses to do — the negative space is as documented as the API. Tone maps are `Record<Tone, …>` so a new enum value is a compile error, not a silent fallback. Accessible names are **required props** (`TableContainer.label`, `IconButton.label`, `Switch.label`), never optional. `min-w-0` appears wherever a flex child could force page-level horizontal overflow. `key={value}` forces remounts of uncontrolled inputs so "Reset" genuinely resets. React 19 style: `ref` is an ordinary prop, never `forwardRef`. Every animation is `motion-safe:` prefixed.

### What the design plans forbid adding

The admin plan's §36 is an explicit do-not-build list: question analytics, pass rates, score distributions or any chart of outcomes; candidate accounts or a candidate-facing result page; email/notifications; proctoring; question deletion, duplication or version history; attempt editing, answer overrides, manual rescoring, status changes, timer extension or attempt deletion; global search or command palette; multi-admin roles or audit log; onboarding tours. Visually: decorative stat cards, gradients, glassmorphism, heavy shadows, hover-lift, more than one primary action per region, icon-only actions without labels, animated counters.

The candidate plan additionally rejects **negative-marking display** (CloudUS has none — rendering "−1" would be a lie), NTA branding, the profile photograph, any proctoring affordance, and **`Toast` on the candidate side entirely**: a candidate reading a question must never have save or timer information appear and then vanish. Exam status must be persistent and in place.

### Component inventory

**`components/ui/`** (shared primitives) — `Alert`, `Badge`/`Chip`, `Button`/`IconButton`/`buttonClass`, `Dialog`, `Input`/`Select`/`Textarea`/`ReadOnlyValue`, `LoadingOverlay`, `Pagination`, `Switch`, `TableContainer`/`Th`/`Td`/`Tr`/`EmptyState`, `ThemeSelect`, `ToastProvider`/`useToast`/`useActionToast`.

`isActive(pathname, item)` is kept free of React and icon imports so the rule can be reasoned about and tested alone. Prefix matching alone gets it wrong twice — `/admin` prefixes every admin route, and `/admin/questions` prefixes `/admin/questions/import` — so `/admin` matches exactly and Questions explicitly excludes the import route while still claiming `/admin/questions/[id]`.

### Accessibility commitments

Radio semantics for options, real `<fieldset>/<legend>`, focus never removed only restyled (two rings: a dark outline carrying the meaning over a white halo so it survives on brand-filled controls), manual focus traps in dialogs with no click-outside-to-dismiss, `aria-live="polite"` status regions that do not re-announce on every phase change, and **no status carried by hue alone** — every state also differs by fill, border weight, text weight or an explicit word.

## 16. Invariants — read before editing

1. **The server is the only authority.** The timer is a display; every write is refused server-side once the deadline passes; `submitExam`'s `intent` never determines the recorded status; the violation count and limit live entirely server-side.
2. **No candidate action accepts an `attemptId`** — it always comes from the hashed session cookie, so there is no argument to tamper with.
3. **Snapshots are authoritative.** `AttemptQuestion` is what scoring, review and both exports read. The live `Question` table is never consulted for a sat attempt, so editing or deactivating a question cannot change a historical result.
4. **Nothing in `lib/admin` writes.** Every query module is read-only; scores are read from persisted columns, never recomputed.
5. **An in-progress attempt never yields an answer key** — the result page returns before loading any snapshot row, and the detail export returns 409.
6. **Each attempt's maximum is its own paper's `_sum(marks)` where `scored: true`**, never a blueprint constant, because sections toggle on and off.
7. **Unrecognised query input never reaches Prisma** — every parser maps it to a safe default, and `Object.hasOwn` is used rather than `in` to block prototype keys.
8. **Client state decides nothing.** Bulk activation re-reads and re-validates from the database; the import payload is rebuilt by `verifyRows`; a tampered checkbox can only change *which ids* are considered.
9. **Error logs never carry the error object** — only `{ name: error.name }`, because Prisma errors can embed the connection string.
10. **Blank ≠ zero** throughout exports and scoring: unfinished or undrawn values are `null`/empty, never `0.00`.
11. **Deactivation is never deletion** for questions; **deselection *is* real deletion** of a `CandidateExam` row, and therefore of eligibility.
12. **Import never activates.** Questions arrive inactive; candidate import never creates `CandidateExam`/`Attempt`/`ExamSession`; selection import never creates or updates `Candidate`.
13. **`terminated` is checked before any terminal status** everywhere, so a terminated attempt never renders as a normal completion.
14. **Marks are strings or integer hundredths, never floats.** The question pipeline keeps `marks` as a string end-to-end; scoring sums in hundredths.
15. **Light mode only**, enforced by the two scope classes. No `dark:` variants in candidate code.
